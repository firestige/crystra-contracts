# Crystra 更名实施顺序

**执行状态与恢复请先阅读 [执行计划](execution-plan.md)。本文只维护任务范围、依赖和退出条件，不另行记录状态。**

日期：2026-09-13。状态：实施计划，尚未执行。本文以本次对话最新约束为准，覆盖分析报告中仍写为“安装器待选／清理工具”的旧措辞。任务编号用于文档内排程，尚未创建 GitHub Issue。

## 目标与范围

- 一个公开 DSH 插件 dsh-crystra，只注册 firestige/crystra-dsh；允许多个内部模块、Loader 行及普通依赖，不另行发布可独立安装的 Intake／Execution／Studio／Suite 插件。
- 优先取消面向 DSH 用户的独立安装器。默认方案为 DSH 安装包，插件完成首次配置、依赖检查、必要服务引导和诊断；现有运维代码按需复用为内部实现，不先机械发布一个新名字的独立 CLI。
- 各组件在自己仓库 main 演进；主仓库 crystra 只组装并发布经过验证的可用组合。组件发布不以主仓库先行 gitlink 为条件。
- 旧制品与历史资产不迁移。已部署旧 WSR 的配置和运行数据在本次切换时人工盘点、打包校验、隔离清理，不开发清理工具、迁移器或长期兼容功能。
- 保留现有数据库与领域组件职责，不为取消安装器同时重做存储架构。忽略组合工作树子模块的未提交变化。

## 排程原则

先确定新安装闭环和命名，再从依赖底层改起。插件先能独立安装和初始化，再切换外部仓库坐标与发布渠道。最后清理实际旧部署，用新制品在真实目标环境验收。

组件内的包名、代码、测试、CI、当前文档一起修改，避免出现新包名搭配旧消费者。跨仓库联调先用精确本地打包制品或明确提交，不临时依赖旧 WSR 下载资产，也不提前要求尚未发布的新 URL 可下载。开发与主线集成在各组件仓库进行；不在组合仓库子模块里推进组件功能。

T2 中 Evidence、Evolution、Workflow Package 可在明确所需 Contracts 输入后分别推进，UI 可提前推进。T5 的文案和资产设计可以穿插进行。表中允许并行表示依赖关系，不意味着另开 Agent 或任务。

## T0：固定实施契约

产出：把 [命名映射表](naming-map.md) 中影响实施的建议落定；形成一页安装旅程和责任表。

1. 复核 8 个远端 main 的实际起点与已有变更；不处理组合子模块脏状态。
2. 核实目标仓库名、包名／scope 与发布权限；选定首轮版本／tag 规则。历史记录不重写。
3. 明确插件从何处取得普通依赖、如何固定后台服务组合、首次创建哪些配置与目录。
4. 默认保留现有服务架构：执行依赖与 UI 随插件分发；后台服务由插件显示检测结果并引导配置，耗时准备有进度和失败状态。
5. 列出旧 product-operations 职责：哪些交给 DSH，哪些复用为插件内部 bootstrap／诊断，哪些仅属于组合发布流水线，哪些可以删除。
6. 只盘点实际旧部署的归属和位置；此时不为方便开发提前清空旧环境。

退出条件：普通用户不需要先装独立产品安装器；若现有能力无法满足，应指出具体前置条件／缺口，不能在实现中悄悄恢复第二安装入口。也不承诺插件会自动安装宿主操作系统的 Docker／Python。

## T1：Contracts 优先

- 更新 scope、现行 Schema namespace／URN、引用和构建工具；不把 candidate 契约因更名升级为稳定契约。
- 将当前仍需维护的契约文档、生成依据放到负责组件或明确的独立资源中，解除从主仓库源码树生成验证输入的要求。
- 重新生成新契约资源／publication，不改旧历史 publication。
- 组件 CI 覆盖 main，自身发布选择自身精确提交；消费者依赖显式固定。

退出条件：从 Contracts 仓库独立执行现行检查并产出可消费的新资源，消费者不再要求旧主仓库目录结构。

## T2：普通组件逐一收口

| 仓库 | 必做项 |
|---|---|
| crystra-execution | 包名／import／配置／状态目录；main CI；消除发布前主仓库先 pin；盘点旧 Intake 适配器独有行为交给 T3，停止单独插件发布 |
| crystra-ui | 库包名、共享 CSS／状态键、构建引用；main CI 取代旧 iter5 分支触发；自身提交决定候选 |
| crystra-evidence | Python 包／模块、数据库初始化与角色、镜像、服务配置；自身提交与固定 Contract 构建验证 |
| crystra-evolution | Python 包／模块、镜像、配置；移除主仓库 gitlink 前置；保留现有计算职责 |
| crystra-workflow-package | 当前资源中的仓库／包／工具引用；main CI；独立文档与固定 Contract 检查 |

消费者同时改动，使用精确本地 tgz／wheel／镜像／契约资源联调；这些是新名称的开发制品，不是旧制品迁移。与 T3 相关的 Skill／工具新名称可先写入待联调资源，T3 完成后闭环验证。

退出条件：每个组件可以独立构建与验证，新生产者和消费者的协议匹配。CLI、README、示例随对应组件同步调整。

## T3：单插件包装和模块装配

- 统一可安装／发布包 dsh-crystra，归属 crystra-dsh；移除三个包数量及发布顺序等旧断言。
- Execution、Studio、init 等代码可独立模块，也可采用普通库依赖；所有 DSH 入口由同一包装配。内部依赖不另行登记为 DSH 插件。
- 合并 Marketplace 对外条目、包配置和版本入口，取消 dshMode 的三模式选择。
- 处理好每个模块配置边界、依赖注入、异步初始化、disposer、timer、RPC、slot、hook 和 workspace UI 替换。
- 从 Execution 仓库旧 Intake 中迁入仍需要而尚未覆盖的功能；不保留旧包名的公开适配层。

退出条件：干净 profile 只安装一个 dsh-crystra 即可获得命令、交付交互与分析视图；内部可多个节点，无重复注册或旧插件依赖；禁用／重载／卸载清理正确。

## T4：取消独立安装器的用户步骤

- DSH 负责插件的安装／更新／移除；插件依赖描述负责普通库。
- 原运维实现中需要保留的配置、服务检查、初始化和诊断逻辑迁入适当内部模块，不另造一套重复实现。
- 轻量 bootstrap 幂等执行；首次拉镜像、初始化服务等操作有可见进度、失败原因和重试入口，不拖住整个 DSH。
- PostgreSQL／Evidence／Evolution 的就绪状态清楚；缺失分析服务时，相关能力显示未就绪，不把执行链路一同锁死。
- 用户首次配置完成后可使用全部现有必要功能；重启不重复安装，不依赖旧全局 WSR 状态。
- 删除正常安装文档中的独立安装器步骤。@crystra/product-operations 与独立 crystra 安装 CLI 不再作为必须发布的预设目标；是否保留内部库由 T0 分工决定。

退出条件：按 README 只有 DSH 插件安装入口，不需要另装产品安装器；从干净环境能配置、运行、诊断和普通卸载。普通卸载保留数据的产品行为与本次旧部署人工清理分开。

## T5：品牌和外部坐标切换

- 当前 README、安装引导、架构图、Banner、social preview、Marketplace 图标统一 Crystra；不改历史截图。
- 在切换前把改名命令、remote／CI／配置修改和权限清单准备齐；协调更名 8 个现有仓库，不新建替代仓库。
- 更新 .gitmodules 的必要 URL／旧品牌路径；不处理其工作树里的未提交内容。
- 更新 Actions 发布仓库、App 权限、包发布绑定、镜像来源与当前安装 URL。实际发布新制品前不得宣称 URL 已可用。
- 移除 Execution 的 dsh-plugin Topic／安装入口身份；crystra-dsh 为唯一插件注册来源。实际市场提交留到制品验证后。
- 本地 checkout 路径更名若影响当前工具／工作目录，安排在协调窗口，不边运行构建边移动目录。project-ops 配置坐标跟随仓库名；不隐含迁移 Issue。

退出条件：新坐标一致，发布权限可用；当前代码与文档没有指向旧制品的有效路径。

## T6：候选制品与组合验证

组件按依赖顺序发布新候选：Contracts → 所需领域组件与 UI／Workflow → dsh-crystra → 组合。某组件的具体依赖以 T0/T1 落定的依赖图为准，不要求无关组件同步版本。

组合仓库固定明确的版本、来源和 digest，仅发布可用组合。若插件需要服务组合清单，采用内置或精确绑定的版本；不能因主仓库以后发布另一套组合而让已装插件隐式改变服务版本。

先在隔离空白环境验证下载制品的安装、启动、交互、故障状态和卸载；不需要先清理用户实际旧部署，也不引入旧系统升级测试。通过的制品及验证结果作为 T7/T8 的切换输入。

退出条件：从远端下载的新制品可重现通过组合验收，不以本地源码联调通过代替发布制品验证。

## T7：人工完成旧部署清理

这是一项本次更名的执行操作，不开发程序、不发布清理命令、不添加迁移框架或清理回归测试。

1. 依据实际部署逐项确认旧配置、状态、DSH 旧包与 patch、运行进程、下载缓存、数据库和卷的归属。
2. 停止相关写入或取得数据库一致性备份；将需要留存的旧数据打包，记录原位置和内容清单，校验可读性与摘要。
3. 解除已确认属于旧 WSR 的插件／配置／服务注册，清理其有效路径；备份放到 Crystra 不会读取的位置。
4. 读回 DSH 配置与服务状态，确认旧内容不再被发现，共享插件和其它项目不受影响。

不把所有名含 wsr 的文件都视为可删；主仓库子模块未提交变化和用户工作文件仍不动。旧远端 Release／镜像的批量删除不是本地切换前置，本计划不将其混入人工清理。隔离档案仅留档，不输入新系统。

退出条件：实际环境没有旧 WSR 活跃入口，新安装不会读到旧配置；有清理记录和已校验的隔离包。

## T8：实际环境安装、验收与发布收尾

- 使用 T6 的精确新制品安装 dsh-crystra，通过插件完成配置／就绪。
- 验证一次真实 Workflow 的创建、执行、交互、结果，以及 Evidence／Studio 必要链路；重启、禁用、卸载行为符合预期。
- 汇总当前名称残留例外、新安装证据、唯一插件身份、实际环境状态和人工清理记录。
- 本次只要求 RC 组合通过联调与实际安装验收，证明更名未破坏内容；不要求发布 GA。后续使用同一份已验证 RC 制品，不能验完后悄悄重建。
- 最后更新公开安装入口，向可访问的 DSH 市场登记／更新唯一 crystra-dsh 条目；外部市场未合入前，不宣称登记已生效。

完成标准：用户只面对 dsh-crystra；各组件 main 可继续独立演进；crystra 仓库发布的是明确可用组合；旧 WSR 部署已人工清理隔离，历史制品未迁移。

## 范围控制

本计划不启动代码修改、仓库更名、停服务、发布或清理。实现阶段遇到安装器取消的具体障碍，先解决最小必要前置；不默认扩大成数据库替换、组件职责合并、自动旧数据识别系统或全新的发布平台。
